# Article summary implementation plan

## 사용자 문제와 범위

사용자가 원문을 열기 전에 핵심 내용을 파악할 수 있도록 수집된 기사 제목과 설명을
근거로 AI가 짧은 한국어 요약을 생성하고 기사 제목 아래에 표시한다.

이번 작업은 다음을 포함했다.

- Collector의 Groq 요약 생성 작업과 수동 실행 API
- Server의 독립적인 요약 작업 상태, 선점·완료·실패 API와 조회 응답
- Frontend의 `AI 요약` 배지와 요약 표시 및 미완료 기사 설명 대체 표시
- 데이터베이스의 멱등 스키마 변경과 각 계층의 자동 검증

원문 페이지 본문 수집과 자동 스케줄링은 이번 범위에 포함하지 않았다.

## 확인한 기존 동작

- `articles.summary` 컬럼과 엔티티 필드는 있었으나 조회 응답과 UI에서 사용하지 않았다.
- Collector에는 태깅 작업만 있으며 요약 생성 진입점이 없었다.
- Server에는 태깅 작업의 재시도 가능한 선점 흐름만 있고 요약 상태는 없었다.
- Frontend는 제목 아래에 수집 출처의 `description`만 표시했다.

## 구현 결과

1. 요약 상태와 메타데이터를 DB 및 Article 엔티티에 추가했다.
2. 동시 Worker에 안전한 요약 작업 선점, 완료, 실패 API를 구현했다.
3. 제목·설명을 정제하여 Groq strict JSON Schema로 한국어 요약을 생성하는 Worker를 구현했다.
4. Collector의 `POST /summarize`로 작업을 수동 실행할 수 있게 했다.
5. 기사 조회 응답에 summary를 포함하고 UI에서 제목 아래에 `AI 요약` 배지와 함께
   우선 표시한다.
6. Collector 단위 테스트, Server 통합 테스트, Frontend 정적 검증과 `./scripts/check`가 통과했다.
7. 실제 기사 1건을 Groq로 요약해 정식 작업 API로 저장하고 공개 조회에서 확인했다.

## 결정과 이유

- 요약 상태는 태깅 상태와 분리했다. 두 AI 작업이 서로의 재시도와 가용성에 영향을
  주지 않게 하기 위해서다.
- 요약 입력은 현재 저장된 제목과 설명으로 제한했다. 원문 본문 수집은 출처별 정책,
  HTML 정제, 저작권 및 실패 처리 범위가 더 크므로 별도 후속 작업으로 둔다.
- 출력은 최대 500자로 제한했다. 설명이 충분하면 대체로 2~4문장 안에서 배경·핵심
  접근·명시된 결과 또는 의미를 필요한 만큼 담고, 설명이 짧으면 추측 없이 1문장으로
  정리한다.
- 새 요약과 기존 DB 요약 모두 간결한 한국어 `~다`체로 통일한다.
- 요약이 없으면 기존 설명을 표시해 점진적인 처리 중에도 정보가 사라지지 않게 했다.
- Hibernate 동적 업데이트를 적용해 태깅과 요약 Worker가 서로 다른 상태를 동시에
  갱신할 때 변경하지 않은 필드를 덮어쓰지 않게 했다.

## 완료 상태와 후속 작업

- 새 기사와 기존 미요약 기사를 선점해 요약을 저장하고 조회할 수 있다.
- 요약 실패는 최대 3회 재시도할 수 있고 기사 목록 조회는 계속 동작한다.
- 기사 카드 제목 아래에 `AI 요약` 배지와 요약이 표시된다.
- 기존 기사 50건의 요약 생성과 DB 저장을 완료했다.
- 원문 본문 기반 요약, 고정 품질 평가와 자동 실행은 기술 부채에 남겼다.
